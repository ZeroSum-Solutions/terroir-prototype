<project_specification>
  <project_name>terroir</project_name>

  <overview>
    Terroir is a wine-management SaaS for restaurants and serious cellars. Staff photograph paper invoices, the system runs Azure OCR + Claude structured extraction to build a typed inventory, and the app surfaces a public wine list, drink-window guidance, pour tracking, and reconciliation against open bottles. Built on Next.js 16 + Supabase + Anthropic Claude, deployed as a single service on Railway.
  </overview>

    <pour_and_open_bottles>
      - Staff can record a pour from /cellar against a specific bottle
      - Opening is an explicit command that consumes one identified same-site source-lot unit and returns a new immutable bottle ID; an active bottle never triggers or blocks an implicit replacement
      - A pour decrements only the selected physical bottle's integer remaining mL; it never spills into another bottle
      - System closes a bottle automatically when remaining drops below a threshold
      - System creates a pour_events row for every pour
      - Contract-2 events mutate by exact bottle ID with site/wine containment; no event trigger updates every open bottle of a wine
      - Undo appends one linked version-2 compensation against an exact eligible event; it never deletes evidence or targets “latest for wine”
      - /cellar/open shows every active physical bottle as a distinct stable identity using its captured capacity and provenance state
      - User can manually open a bottle without recording a pour (e.g., for tasting)
      - Measured close and discard act only on the selected immutable bottle ID; discard records its exact remainder as spill and is not a measured closeout
      - Fresh physical open, pour, spill, close, discard, and undo writes use execute_physical_bottle_command; completed version-1 receipts remain replay-only
      <compatibility_note>record_pour is retained only as additive legacy compatibility and is not an authorized write path for new callers.</compatibility_note>
      - Insufficient selected-bottle volume is non-mutating and never auto-opens, splits, or substitutes another bottle
      - Venue-managed presets are positive integer-mL snapshots and include tasting sizes; editing a preset cannot change an in-flight service action
      - User can record a pour in a custom amount
      - User can attach a note to a pour event
    </pour_and_open_bottles>

    <reconciliation>

      - User can enter the actual remaining volume for each open bottle
      - Reconciliation variance is written as an exact-bottle version-2 event/effect under one batch receipt, not through the retired scalar wine-only RPC
      - Every reconciliation, including one bottle, uses one all-or-none execute_physical_reconciliation_batch call and one immutable operation UUID/payload
      - Each committed reconciliation entry has exact bottle/wine event and effect evidence; no availability event is allowed to stand in for physical identity
      - System highlights variances exceeding a configurable threshold
      - User can view reconciliation history with variance trends
      - The database revalidates current manager/owner authority for execution and exact replay; route UI state is not the authority

      - System stores exact POS event replays idempotently, records changed-body conflicts separately, and prevents older or contradictory snapshots from replacing accepted interpretations
      - System abstains from automated POS mapping when selection identity, quantity, unit, occurrence time, or reviewed conversion is missing and keeps operator corrections as linked interpretation versions

    <offline_lookup_foundation>
      - System stores only an explicit cost-free cellar lookup projection and a local display context, without cached roles, capabilities, notes, prices, staff data, or arbitrary API and RSC payloads
      - System fails closed on expired local display leases, detected clock rollback, corrupt or ambiguous partitions, and storage denial without treating the at-most-twelve-hour display lease as server authorization or trusted hardware security
      - System atomically provisions the current server-derived actor and site partition while locking every other partition, using only replaceable contexts and projections in IndexedDB version one
      - System reports the public offline shell ready only after credentialless direct-success caching of its exact same-build assets and public icons, never caching private HTML, API responses, RSC, uploads, redirects, or mutations
      - System immediately blanks private UI on sign-out and distinguishes verified local locks, failed local persistence, and pending or completed server sign-out without claiming secure erasure or durable locking when both local writes fail
      - Staff can search the cached cellar with all authorized placements, inventory quantities and projection age visible, without cached lookup implying real-time stock or offline mutation support
      - GET /api/offline-context returns only the explicit lookup allowlist and a bounded display context after current session and active-site membership checks, ignoring client-claimed identities and returning no-store responses
    </offline_lookup_foundation>

    <physical_bottle_inventory>
      - Each contract-2 open bottle has an immutable ID, captured positive nominal capacity, exact site/wine containment, state version, opening operation, and known same-site source lot; promoted legacy bottles keep explicit unknown provenance
      - Multiple physical bottles of one wine may be active, and every service mutation selects one exact bottle without defaulting to first, newest, fullest, or remembered
      - Every contract-2 pour, spill, reconcile, close, discard, and undo event/effect is receipt-linked and bottle-exact; one command increments the selected bottle version once
      - Exact-bottle reconciliation is one canonical UUID-sorted, wine-before-bottle locked, all-or-none batch whose changed-payload UUID reuse conflicts and whose exact replay returns stored ordered results
      - Phase C switches the normative inventory contract from 1 to 2 as the final statement of the writer/trigger/ACL transaction; fresh version-1 or wine-only writes then fail while completed version-1 receipts remain byte-stable and replayable
      - Discard records one exact-remainder spill plus a distinct discard receipt/effect, closes only that bottle, creates no measured closeout/replacement, and increments its version once
      - Undo is an append-only linked compensation with a fixed 15-minute window; correcting discard requires mistaken_report and confirmation that the same bottle remains, while actual discard, uncertainty, later activity, or a version-1 target is non-mutating review/error
      - Exact-bottle readers are tenant-constrained security-invoker projections without raw opener IDs or lot cost; aggregate/effective readers sum duplicate bottles and exclude reversals from sales without deleting history
      - Physical source-lot provenance blocks import, invoice, and direct lot deletion; wine merge repoints relational dependencies without changing receipt JSON bytes
      - Venue-managed pour and tasting presets preserve positive integer-mL line snapshots and permission checks through execution and retry
      - Flight and split-pour lines retain wine, physical bottle, amount, operation-line identity, and explicit recorded/pending/failed status without silent substitution
      - Bottle/table holds reserve an identified sealed unit or open bottle with audited reserve/release/consume/expire transitions and server-authoritative exclusivity
      - Optional sealed tags attach one-to-one to an existing lot unit without increasing lot quantity, preserving provenance and duplicate-scan/retag audit
      - POST /api/open-bottles performs an idempotent explicit open and returns the exact new bottle; another active bottle does not block the operation
      - POST /api/open-bottles/close performs an idempotent measured close on one exact bottle with actual volume, write-off, and reason
      - POST /api/open-bottles/[id]/close performs an idempotent discard on the path's exact bottle and returns its linked spill/discard evidence
      - POST /api/pour/undo requires an operation UUID and exact reversal event, enforces compensation/review rules, and returns the exact bottle and reversal event
      - POST /api/reconcile preserves the entire failed or uncertain batch draft and clears it only after validated atomic success or exact replay
    </physical_bottle_inventory>

    <csv_identity_review>
      - User can preview CSV rows and deterministic LWIN candidates before any write, see apply-eligible candidates with scores and reject or undo in incremental batches, keep below-threshold candidates unlinked, and have confirm re-parse and re-match content and veto an apply-eligible link when the supplied reviewed candidate set, including an empty set, omits or disagrees with the current candidate
      - System may, after an explicit operator request for one currently displayed apply-eligible candidate, rederive the global candidate from bounded producer/cuvee text and return an optional display-only supported, review-recommended, or unavailable advisory bound to the current row/candidate view; the advisory never creates or promotes a candidate, changes approval, rejection, or import writes, or blocks deterministic preview, confirm, or apply when unavailable
    </csv_identity_review>

  <key_interactions>
    <invoice_scan_flow>
      1. User taps Scan FAB on mobile, captures invoice photo
      2. App uploads image to Supabase Storage
      3. App POSTs scan reference to /api/scan
      4. Server runs Azure OCR, then sends text to Claude with extraction prompt
      5. Server validates Claude response with Zod
      6. Server upserts wines via find_or_create_wines_batch
      7. Server creates invoice_scans + inventory_items rows
      8. Server enriches new wines via match_lwin_batch and enrich_wines_batch
      9. Client navigates to scan-review screen with editable line items
      10. User confirms or edits, then commits to inventory
    </invoice_scan_flow>
    <pour_flow>
      1. Staff opens the cellar, selects one physical bottle or explicitly opens a new one from an identified sealed lot, then chooses an integer-mL amount
      2. Client stores one operation UUID and immutable exact-bottle or predecessor-opening payload before POSTing to /api/pour
      3. The physical command revalidates site, wine, bottle, source-lot, authority, and expected version before one atomic mutation
      4. An uncertain response keeps the same UUID and payload for retry; exact replay returns the stored bottle and event without another stock change
      5. Only a validated success or exact replay clears the pending action and refreshes inventory and bottle indicators
    </pour_flow>
    <publish_list_flow>
      1. User edits sections and items in /lists/[id]
      2. User toggles Published, system validates slug uniqueness
      3. Public route /list/[slug] renders for guests with cache headers
      4. Auto-86 logic hides or marks unavailable wines based on cellar_config
    </publish_list_flow>
    <reconcile_flow>
      1. Manager opens /cellar/reconcile at end of shift
      2. UI lists every active physical bottle with exact ID, remaining mL, captured capacity, and frozen state version
      3. Manager enters target remaining mL while the client retains one UUID and the complete canonical batch draft
      4. Client POSTs the all-or-none exact-bottle batch to /api/reconcile, including a one-bottle batch
      5. The server locks and revalidates the complete sorted set, then commits one receipt and ordered bottle/event/effect results or rolls back every entry
      6. Failure or uncertainty preserves the entire draft and original UUID; validated success or exact replay clears it
    </reconcile_flow>
  </key_interactions>
