## What exists and is reusable

- **[VERIFIED PRESENT — identity]** Terroir has a global `canonical_wines` identity at producer+cuvée grain and tenant-scoped `wine_variants` at canonical wine+vintage+size, with LWIN/GTIN fields; operational `wines` rows point to both (`supabase/migrations/0097_canonical_wines.sql:1`, `supabase/migrations/0097_canonical_wines.sql:123`, `supabase/migrations/0098_wine_variants.sql:1`, `supabase/migrations/0098_wine_variants.sql:24`, `src/types/database.ts:2118`). Reuse the identity-resolution rules and explicit ambiguity/provisional behavior as evidence for E-005/E-007, but do not assume the legacy restaurant-scoped variants are the rebuild's final business/venue model.
- **[VERIFIED PRESENT — stock/location]** `inventory_items` carries wine, tenant, quantity, unit cost/currency, package text, `bin_id`, legacy `bin_location`, section, source invoice and added time; `bins` carries code, zone and capacity (`src/types/database.ts:147`, `src/types/database.ts:754`). `/api/search` tenant-scopes cellar results, aggregates quantity, and returns only the most recently stocked bin (`src/app/api/search/route.ts:155`, `src/lib/unified-search/merge.ts:22`). `/api/cellar/grid` returns every placed inventory row grouped by normalized `bin_location` (`src/app/api/cellar/grid/route.ts:13`). `resolveCellarContext` already derives all distinct legacy locations and weighted cost from inventory rows (`src/domains/wine-profile/resolve-cellar-context.ts:87`). These are useful read/projection patterns, not proof of an exact ledger or lot model.
- **[VERIFIED PRESENT — notes/ratings]** House notes store tenant, wine, author, body, optional 50–100 score, tasting date, and confirmed descriptors (`supabase/migrations/0148_wine_notes.sql:64`, `src/domains/notes/note-service.ts:22`). The house profile counts human-confirmed descriptors and separately reports the number of scored notes (`src/domains/wine-profile/resolve-house-profile.ts:53`). X-Wines provides external community aggregate and vintage aggregate ratings (`src/types/database.ts:2300`, `src/types/database.ts:2408`). These sources must remain distinct.
- **[VERIFIED PRESENT — acquisition evidence]** Inventory rows can link to committed invoice scans with distributor and invoice date, and `/api/wines/price-comparison` exposes those per-wine cost observations (`src/types/database.ts:754`, `src/types/database.ts:931`, `src/app/api/wines/price-comparison/route.ts:12`). This is restaurant receiving/cost evidence, not a personal purchase history; manual/imported rows may not represent a purchase.
- **[VERIFIED PRESENT — deterministic assistant/search]** `GET /api/assistant?q=` is model-free, single-turn filtering over the tenant cellar, with corpus fallback (`src/app/api/assistant/route.ts:1`, `src/app/api/assistant/route.ts:75`). It understands region, grape, vintage, pairing, body and explicit monetary bounds (`src/lib/wine-intelligence/assistant-query.ts:62`, `src/lib/wine-intelligence/assistant-query.ts:136`), then ranks by in-stock, X-Wines community rating and depth (`src/lib/wine-intelligence/assistant-match.ts:126`). Unified `/api/search` adds fuzzy cellar/LWIN/X-Wines retrieval and honest identity-key dedupe (`src/app/api/search/route.ts:248`, `src/lib/unified-search/merge.ts:1`). This is a strong grounded-retrieval base.
- **[VERIFIED PRESENT — commercial pricing only]** `pricing_recommendations` stores restaurant price actions with rationale/evidence (`supabase/migrations/0065_pricing_recommendations.sql:10`). Its rules use appreciation, pour velocity, gross margin and cellar-health state (`src/lib/pricing-recommendations/recommend.ts:26`, `src/lib/pricing-recommendations/recommend.ts:69`). This must not feed personalized taste ranking as if it were preference evidence.

## What is absent or insufficient

- **[VERIFIED ABSENT IN GENERATED CONTRACT/TARGETED SEARCH]** No personal profile/preferences, acquisition-history, conversation/message/memory, embedding, vector-index, or personalized-recommendation table/RPC is present. The current assistant explicitly defers embeddings, vector indexes, open-ended chat and multi-turn search (`src/lib/wine-intelligence/assistant-query.ts:4`).
- **[VERIFIED GAP]** “Where is our Borello?” can fuzzy-resolve a cellar wine and return one representative bin, or use the grid for all legacy rows, but the voice resolver deliberately returns `locations: []` because authoritative placement has not landed (`src/app/api/cellar/voice-resolve/handler.ts:252`). There is no explicit lot identity, room/custody hierarchy, or immutable stock event+receipt authority in the current contract.
- **[VERIFIED GAP]** “Napa Cab under budget based on 9 genuine ratings/purchases” currently filters cellar region/grape/`retail_median`, then ranks using external community ratings; `/api/assistant` never reads `wine_notes`, invoice receipts, or a user profile (`src/app/api/assistant/route.ts:84`, `src/app/api/assistant/route.ts:128`). It therefore cannot truthfully make the stated personalized claim.
