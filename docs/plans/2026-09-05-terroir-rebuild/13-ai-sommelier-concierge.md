# Terroir AI sommelier and concierge

**Design proposal, September 5, 2026.** This extends the existing planning package. It does not approve Gate 1, change the proposed manual-receiving evaluation, or install an AI service. Public source facts, current repository observations and proposed product choices are distinguished below.

**Recommendation:** build one conversational interface over three controlled services: live cellar lookup, personalized wine recommendation, and cited wine knowledge. Keep authoritative data and memory in Terroir's Postgres database. Start recommendations with explicit preferences and wine attributes; add learned collaborative models only when measured evidence supports them.

This design can support the whole wine community without treating everyone as the same customer. Personal taste, restaurant procurement, supplier offers and public discovery share wine identity but keep separate purposes, permissions and evidence.

**What the two examples require**

For “Where did we store our Borello?”, the assistant resolves the name against the authorized catalog, asks for clarification if several wines or vintages match, and calls a live inventory lookup. It returns every permitted location containing that exact wine/package: venue, cellar/storage area, bin, quantity and record freshness. Third-party custody appears only after its separate E-042 admission, when recorded and authorized. If placement is unknown, it says so. A retailer where the bottle was bought is acquisition provenance, not its current storage location.

The model never answers location from a remembered conversation. Moving a bottle after yesterday's chat must change today's answer. Exact locations and quantities should appear in cards assembled from database results, with a link to the cellar record. A conversational introduction cannot invent additional bins or stock.

For “I'm looking for a red Cabernet from Napa,” the assistant first determines whether the user wants something in their cellar, on the restaurant's list or available to buy. It applies those constraints, the current budget and any stated occasion before ranking. An explanation can cite actual wines the person rated highly and the attributes they share. Every claimed preference has supporting records.

“Based on your last nine wines” is allowed only when there are nine eligible, distinct wine editions (the counting rule below) in the selected context. The response identifies their mix: ratings, purchases or other signals. Ratings alone contain no purchase price. Buying for a restaurant, buying a gift, holding inventory and liking a wine are distinct events. Explicit budget wins; a historical spending range is only a suggested default from comparable personal purchases and must be presented for correction.

**Verified starting point**

The current repository has a deterministic `/api/assistant` that parses wine constraints and ranks using stock plus external community ratings. It has fuzzy search, identity links, authored house notes with optional 50–100 scores, and invoice-linked acquisition/cost observations. These are useful foundations, not personal taste memory. The assistant does not currently read a personal history to support the requested explanation. Evidence: `src/app/api/assistant/route.ts:1`, `src/lib/wine-intelligence/assistant-match.ts:126`, `supabase/migrations/0148_wine_notes.sql:64`.

Search returns one representative, recently stocked bin, and the voice resolver returns no authoritative placements. Existing `/api/cellar/grid` and `resolveCellarContext` already provide all-location shapes over legacy inventory. The missing authority is the target lot/custody/ledger model; reuse these read patterns only through its approved projection, with field-specific cost grants. Evidence: `src/app/api/search/route.ts:155`, `src/app/api/cellar/voice-resolve/handler.ts:252`, `src/app/api/cellar/grid/route.ts:13`, `src/domains/wine-profile/resolve-cellar-context.ts:87`. No personal-memory, embedding or personalized-recommendation persistence contract was found in the generated database contract and targeted search. **Three architecture choices**

| Approach | Strength | Cost or limitation | Decision |
|---|---|---|---|
| Postgres authority, typed tools, explicit preference/content ranking | Fits the application, works before community-scale feedback exists, and keeps deletion and permission checks in one authority | We must define wine attributes, evidence and product-specific ranking | **Recommended foundation** |
| Dedicated memory and recommendation services immediately | Reuses orchestration and learned-model features | Adds stores, migrations, authorization surfaces, synchronization and hosting before value is established | Defer until a measured requirement justifies a particular service |
| General autonomous agent querying databases and maintaining its own memory | Flexible demonstrations | Hard to guarantee exact stock, purpose boundaries, deletions and explanations | Reject as the production data-access design |

The LLM may choose among typed, allowlisted tools. Server code supplies authenticated scope and executes validated queries. It receives no arbitrary SQL, service-role capability or unrestricted filesystem/browser access. The [AI SDK documents schema-validated tool calling](https://ai-sdk.dev/docs/ai-sdk-core/tools-and-tool-calling); validation alone is not authorization. Its inspected [repository license](https://github.com/vercel/ai/blob/main/LICENSE) specifies Apache-2.0. Public npm metadata captured for [`ai` 7.0.93](https://registry.npmjs.org/ai/7.0.93) and [`@ai-sdk/provider` 4.0.10](https://registry.npmjs.org/@ai-sdk%2Fprovider/4.0.10) also declares Apache-2.0; a provider-specific adapter is not yet selected. GitHub classified the root license as NOASSERTION, which does not establish different package terms. Evaluate a compatible pinned version as a thin TypeScript adapter, with provider portability and a strict tool/turn/time budget; these metadata observations are not install instructions.

**Where memory, ratings and recommendations live**

The following are conceptual entities, not applied tables or migration names. The schema owner chooses the final tables and constraints when the relevant slice is admitted.

| Entity | Stored fields and relationships | Authority and retrieval |
|---|---|---|
| **Taste profile and permissions** | Single-actor personal profile ID, owner, purpose, personalization consent and privacy revision; existing business/venue membership remains separate | AI-2 adds no household sharing or cross-context import grants. Business-owned house notes retain business permissions and do not become personal evidence. Server derives scope; a supplied profile ID grants nothing. The required group/business/venue boundaries remain intact. |
| **Explicit preferences** | Profile, attribute/value, strength, occasion, source statement/confirmation, validity, revision | “Avoid heavily oaked wines” is editable user intent. Current explicit constraints outrank inferred affinity. |
| **Tasting and rating records** | Profile, author, exact wine/vintage when known, original value and scale version, note, confirmed descriptors, tasted/recorded times, visibility and correction lineage | Personal, house and external critic/community ratings stay separate. Derived normalization is versioned; raw scales are never silently averaged. |
| **Personal acquisition and experience records** | Actual purchaser/profile and purpose, wine/package, quantity, actual paid amount/currency, purchase date, source verification, gift/refund status, links to a tasting experience | An invoice or cellar import is not automatically a personal purchase. Related purchase, tasting and rating signals can reference one experience to prevent double-counting. |
| **Recommendation exposures and feedback** | Request/profile/context, candidate IDs and shown order, model/policy version, exposure ID, event type, selected reason, event time | Record what was shown before interpreting clicks or dismissals. Unseen wine is unknown; a dismissal can mean price or occasion, not bad taste. |
| **Derived taste features** | Attribute affinities, supporting evidence IDs, counts/conflicts, calculation version, built-through event revision | Rebuildable projection, not a second truth. Cold-start and stale profiles fall back to explicit preferences and current request. |
| **Memory assertions** | Profile, claim, explicit/inferred status, source IDs, created/valid-from/valid-to times, confirmation, contradiction/supersession, revision | A compact contextual summary points back to evidence. Inference never rewrites a rating or becomes a hard preference automatically. |
| **Conversation/session state** | Scoped session, bounded turns, current intent/occasion/budget, referenced record IDs, expiry and privacy revision | Conversation context is short-term. Persistent preferences require an explicit request or product-approved confirmation flow. Context switching starts a fresh scope-bound session. |
| **Knowledge and retrieval chunks** | Canonical wine/producer/region, source and rights, text/version, audience, expiry/withdrawal, embedding configuration and source revision | Public licensed knowledge and private notes are separate retrieval collections or rigorously scoped relations. Costs and supplier terms are not general knowledge chunks. |
| **Recommendation decision record** | Parsed hard constraints, candidate source IDs, policy/model versions, permitted feature contributions, evidence references, confidence/abstention, source freshness | Supplies reproducible reason cards and quality evaluation. Store bounded evidence references rather than duplicating sensitive prompts indefinitely. |

Enforce original rating-scale bounds, exact positive acquisition quantities, unique imported source-event IDs, and unknown vintage versus non-vintage distinctions. A rating may link to an acquisition, but neither implies the other. Price observations also retain channel, package size/count, tax/shipping basis and observation time; cross-currency comparison requires an explicit dated conversion policy.

For personal rating UX, propose quick like/dislike plus optional stars and descriptive tags. Preserve the existing house-score convention separately. The precise personal scale is a product choice to test, with `scale_version` stored from the first record. A structured descriptor such as acidity or oak remains an attributed observation, not an objective fact simply because a model extracted it.

Persist either the eligible candidate set or sufficient catalog/stock/price snapshot versions to reconstruct eligibility before using a run for learned-model evaluation. An exposure log of displayed wines alone cannot establish which unseen wines were available then. Runs lacking that evidence are excluded from temporal training/evaluation claims.

**Proposed fixed counting contract for AI-3:** “last nine wines” means up to nine distinct wine editions in the selected personal profile. An edition is canonical producer/cuvée plus vintage with explicit known-year, non-vintage or unknown state; bottle size and repeated bottles do not create another edition. Unresolved identities are excluded until resolved and the excluded count is disclosed. Eligible signals are an authored personal tasting/rating or a verified personal acquisition for personal consumption; gifts, restaurant procurement, imports without confirmation, views and external ratings are excluded. For each edition, select its latest eligible event by occurred-at descending, recorded-at descending, then stable event ID ascending. Order editions by those representative events using the same key, then take nine. There is no implicit date cutoff; apply any requested window and display the actual date range. The schema owner defines this edition projection over canonical identity rather than reusing package-grained wine_variants. Unknown-vintage events for the same cuvée share one edition; the UI discloses that aggregation. Repeated tastings remain separate source events but count once per edition. An acquisition and rating share an experience only through an explicit link, never a same-date heuristic. Imported event IDs prevent replay duplicates. “Nine experiences” would be a different, explicitly labeled query. Each reason cites its actual supporting subset; budget suggestions disclose the smaller comparable paid-acquisition sample, never imply that rating-only events contain prices. If only two rated wines have usable descriptors, the system cannot imply all nine support that taste inference. For price suggestions, compare actual personal purchase prices on a consistent bottle/package basis and currency; disclose the sample and period. Do not blend restaurant menu prices, wholesale costs, public estimates, case totals and personal retail spend.

**Memory lifecycle and control**

Give users “Why do you think this?”, edit preference, remove a rating, forget a memory and disable personalization controls. Business records follow business ownership; leaving a restaurant must not copy its notes or supplier terms into a former employee's personal profile. Copying across contexts, household sharing and gift-recipient profiles are later separately scoped features; AI-2 does not offer them. A gift request may use preferences stated by the current user without accessing a recipient account.

Use distinct controls with an explicit preview of what each does. **Forget this inference** deletes the selected assertion, its derived copies and caches and suppresses its regeneration from the same source revisions; it leaves original ratings/acquisitions intact. **Delete this rating or personal acquisition** erases that source and its derived personal features, embeddings, summaries and dependent recommendation evidence. It never alters business receipts or stock. **Disable personalization** stops reading personal signals, collecting new personalization events and scheduling related jobs; it is not erasure, and the UI says retained history remains. Re-enabling requires an explicit action. **Erase personalization history** deletes all personal preferences, assertions, derived features, profile-linked runs, exposures, feedback, eligibility snapshots/links, sessions and trace content; it also retires trained artifacts containing those signals until rebuilt. Original personal ratings/acquisitions remain only if the user explicitly chooses that clearly labeled option in the deletion preview; otherwise they are included. An operational business record follows its separate ownership/retention policy and is not described as erased by a personal control.

Per-store disposition for full personal erasure: delete raw signal content selected above; delete memories/features/embeddings; delete profile-linked exposures and feedback; delete recommendation decisions and personal candidate snapshots; remove links to any shared catalog snapshot. A shared, nonpersonal catalog snapshot can remain, but no surviving profile linkage may reconstruct that person's choices. Delete sanitized transcripts and personal trace content too. Retain only minimal non-content suppression/erasure receipts, with restricted access; they are not usable for recommendations. These are proposed product policies, not a claim that a deletion system exists. Every slice must prove erasure coverage for each store it introduces through `SAFE-ERASE`; `PRIV-ERASE-ALL-STORES` is the consolidated integration gate, including backup restore and late jobs. No de-identification exemption is assumed for behavioral histories.

Correction supersedes a source version and recomputes dependent features. Keep a minimal non-content tombstone/epoch where needed to prevent replay from recreating deleted memory. A late extraction job must compare source and privacy revisions at commit and fail when stale. A request already in flight must recheck those revisions before showing its answer. Restore procedures replay suppression revisions before personalization resumes; backup expiry is separate from live-store erasure. Do not describe a soft-delete flag or a temporal “invalid” marker as completed erasure.

Persist sanitized session text and typed evidence references; hydrate volatile tool cards afresh. Exclude bins, stock quantities, current prices, supplier terms and credentials from durable memory extraction. Retained user text can contain old facts and must never serve as the authority for a new operational answer. Apply the selected retention policy to transcripts and model traces too.

For external inference, create a bounded authorization/evidence ticket and recheck it immediately before sending data. Revocation blocks new admissions and suppresses stale in-flight responses. A provider may already have received a previously admitted request; ordinary repeated SQL checks cannot promise zero bytes after revocation commits. For `SAFE-REVOKE`, record external egress as not applicable with configuration evidence while no external private-data path exists. Admitting one requires a specified and tested protocol: revocation prevents new admissions, stale responses are suppressed and previously admitted sends are accounted for. A stricter zero-send-after-revocation guarantee requires a coordinated egress/revocation barrier and an explicit provider contract; it is not implied by the baseline policy.

Future collaborative training needs a training manifest, allowed-source policy and a withdrawal/retraining procedure before admission. A retired model or restored backup must not reactivate deleted personalization. Proposed defaults: transient session context expires after 24 hours; saved chat history is off; content-bearing model traces are off; consented recommendation runs/exposures/feedback expire after 90 days unless erased sooner; user-managed ratings/preferences persist until changed or deleted. Eligibility evidence needed for retained runs expires with those runs. Under this default, AI-6 temporal experiments are limited to the retained 90-day eligible window. If that window is insufficient, defer the experiment; extending retention requires a separate documented decision and fresh consent/erasure basis before collecting a longer history, never reconstruction of expired records. Non-content operational/security receipts follow an explicitly documented separate retention policy. These retention defaults must be ratified at slice admission. Provider-side deletion/retention must be explicitly selected; this research has not certified a provider's behavior. The product memory belongs in Terroir's own deployment, not the workstation's cross-project mem0 store.

**Inference location and knowledge corpus decisions**

Default architecture: private text processing, including embeddings, reranking, memory extraction and any private-data conversational generation, stays inside the approved production account/region boundary. No runtime has yet been provisioned there. Until capacity, operating cost and data policy are validated, private semantic/generative features remain disabled and SQL/lexical reads plus deterministic cards serve the user. An external private-data provider requires an explicit boundary/policy amendment; mere API availability or a coding subscription is insufficient. Private records never move to the developer Mac, general CI or an unapproved research service.

Index construction, scheduled re-embedding and memory jobs are inference/data-transfer operations too. Each batch uses bounded purpose/scope/source-revision tickets; recheck before dispatch, at commit and before readout, with cancellation/invalidation on withdrawal. Only synthetic fixtures may leave the approved production boundary under the existing S rule. A separate future trial may use independently sourced, non-production-derived, rights-approved public text after admission; this proposal does not amend S or permit a production-derived export. Hosting, embeddings, reranking, generation, storage and batch work all count toward the operating budget; there is no assumed free production model lane.

AI-4 depends on a named proposed corpus, `terroir-reference-v1`: owner-authored reference entries plus source-licensed text whose manifest records publication and processing rights, permitted audience, source versions and withdrawal handling. It does not exist as an approved corpus yet. Start evaluation with a separately labeled synthetic/owner-authored fixture. Private authored house notes require a separate approved manifest and processing basis; workspace membership alone is not permission to redistribute them. No existing X-Wines aggregate or WineSensed page is silently promoted to reference prose. Corpus approval and hosting are gates before a real-text embedding trial or AI-4 calendar estimate.

**Retrieval process**

1. **Resolve intent and scope.** Bind actor, selected profile, business/venue capabilities and purpose on the server. Parse wine/grape/region, budget, occasion and source mode. Clarify ambiguous identity or purpose with a short choice.
2. **Choose the authoritative path.** Stock, locations, quantities, grants and current offer facts use typed SQL/RPC reads. Personal ratings/preferences use structured profile queries. Descriptive questions use authorized knowledge and notes. A dynamic fact is never sourced only from a vector or chat summary.
3. **Retrieve within permission boundaries.** Use exact identity/aliases and structured filters first. For free-text knowledge, union PostgreSQL full-text candidates with vector candidates and fuse their rankings. Supabase documents this [hybrid search pattern](https://supabase.com/docs/guides/ai/hybrid-search) and [RLS-based vector access control](https://supabase.com/docs/guides/ai/rag-with-permissions). RLS applies only under the correct role; service-role and owner bypasses remain explicit review items.
4. **Rank for the actual task.** A text reranker scores passage relevance. A wine recommender ranks eligible wine choices using taste/context evidence. Those are different scores and must not be confused. Authorization and field-level restrictions apply before any external model sees candidates, not just before the final UI displays them.
5. **Revalidate and explain.** Recheck current permissions, privacy/source revisions, stock and offer freshness before assembling the response. Read stock/placement from a consistent snapshot and show its fetched-at/version marker; “live” means recorded state at that read, not a guarantee against a subsequent physical move. Render exact facts from trusted result fields. The LLM can explain supported reasons, link sources and state uncertainty; reject unsupported identities, numbers or personal-history claims.

Start private vector search with exact search over a bounded authorized set where practical, and benchmark before choosing an approximate index. [pgvector documents](https://github.com/pgvector/pgvector) that approximate scans apply filters after scanning, which can reduce recall; iterative scans can help but do not replace authorization. The inspected [pgvector LICENSE](https://github.com/pgvector/pgvector/blob/master/LICENSE) is the permissive PostgreSQL License; GitHub metadata returned NOASSERTION, so the file text is the evidence. Cross-tenant approximate indexes also need recall/isolation evaluation. Do not promise a complete result set merely because a similarity query returned some rows.

Every embedding index records model ID, immutable revision, dimensions, normalization, query/document instructions, chunker version, source content hash and permissions revision. Re-embedding builds a new compatible index and switches after evaluation; vectors from different configurations are never mixed.

**Recommendation process**

Begin with a transparent content-based system: enforce source-mode and hard constraints; generate eligible candidates; rank using explicit preferences, confirmed tasting attributes and current occasion; diversify genuinely similar results; then explain with record-backed reasons. Separate an objective wine feature, a subjective descriptor and a person's affinity. A new user can specify budget/style/occasion or name a few wines they enjoyed. Without personal evidence, offer clearly labeled contextual recommendations.

A historical purchase is a separate signal, not proof of liking. Repeated purchases may still reflect a restaurant contract or a gift. Keep the raw evidence type and learn its usefulness through evaluation. Do not assign arbitrary weights a scientific meaning or present similarity scores as calibrated probabilities of enjoyment. Paid placement and commercial margin must not influence the organic taste score. Sponsored slots require separate labeling and must not change organic ranking, preserving E-061. Exclude the existing `pricing_recommendations` store (commercial margin, appreciation and pour velocity) from personal taste features; it is not this recommender (migration `0065_pricing_recommendations.sql:10`, `src/lib/pricing-recommendations/recommend.ts:26`).

Later, combine content candidates with item-to-item or collaborative candidates when eligible behavior is sufficiently informative. Google's documentation separates [candidate generation](https://developers.google.com/machine-learning/recommendation/overview/candidate-generation) from the rest of recommendation. The architecture preserves that replaceable boundary; an LLM explanation is not a trained recommender.

**Memory frameworks: what to borrow**

[Mem0](https://github.com/mem0ai/mem0) offers scoped memory retrieval and documented [deletion operations](https://docs.mem0.ai/core-concepts/memory-operations/delete). Its user-ID filter is not Terroir authorization. Borrow the distinction between user/session memory and explicit lifecycle operations; evaluate a library adapter later if it reduces work without becoming a second authority.

[Letta](https://docs.letta.com/guides/agents/memory/) persists agent state and injects core memories into context. Its repository reports Apache-2.0. The context-block idea is useful, but a stateful agent runtime adds obligations beyond this first concierge. An agent-editable memory block cannot replace authoritative preferences or a live stock lookup.

[Graphiti](https://github.com/getzep/graphiti) tracks temporal facts and source episodes. Its Apache-2.0 framework adds a graph backend; its documented invalidation preserves old facts rather than deleting them. Borrow provenance and validity concepts now. Reconsider the graph engine if real questions require multi-hop relationship reasoning that relational joins and retrieval cannot serve. The shared wine/producer/region relationships already fit a relational model; a wine community does not by itself require a graph database.

**Evaluation and release rules**

Use separately frozen retrieval and recommendation tests. Retrieval cases include typos/diacritics, aliases, ambiguous vintages, multiple locations, multilingual requests, unsupported facts, permission changes and malicious instructions embedded in source text. Compare lexical SQL with each semantic configuration on the same permitted records. Measure relevance/recall, wrong identity, citation support, fallback behavior, p50/p95 latency, peak total memory and deployment cost. Freeze thresholds before testing; none of these measurements has been run in this research.

For learned recommendations, use chronological splits and historically eligible candidates. Include new/sparse users and new wines, keep personal and business purposes separate, and avoid sibling-vintage or future-feedback leakage. Evaluate ranking alongside constraint satisfaction, diversity, catalog coverage, popularity concentration, abstention and explicit post-choice satisfaction. Purchases and clicks are imperfect, exposure-biased proxies. Small-data offline wins require a supervised trial before production promotion.

A common blocking safety suite applies to **every slice**, including any model-free path: `SAFE-SCOPE` (forged actor/profile/business/venue IDs), `SAFE-REVOKE` (permission/privacy change mid-request), `SAFE-FIELDS` (cost and supplier-term leakage), `SAFE-TEXT` (instructions in wine names, notes and tool/source text), `SAFE-ERASE` (deletion/retry/restore races) and `SAFE-OUTAGE` (provider timeout and bounded fallback). A surface genuinely absent from a slice may be marked not applicable only with reviewed evidence, not silently omitted.

Proposed fixed policy: zero observed wrong-identity answers, unauthorized location disclosure or cost/term leakage in AI-1 acceptance cases; zero hard-constraint violations or fabricated supporting evidence in AI-3 acceptance cases. Any occurrence fails release. This is a test gate, not a universal accuracy guarantee. Performance/recall targets must be agreed before executing comparisons. Deterministic permission, deletion, exact-stock and evidence-provenance tests must pass regardless of ranking quality. In-flight revocation, queue retry, model outage, duplicated feedback, withdrawn knowledge and stale offers belong in the test matrix. A favorable generic embedding benchmark cannot waive any of these checks.

**Evidence and review**

This is a researched design, not implemented or benchmarked software. The companion review record preserves initial findings, root verification, corrections, named-model receipts and final dispositions. The companion feature/database matrix maps 14 capabilities to existing outcomes without changing the 68-outcome baseline. Factual sources were captured from primary documentation, GitHub/Hugging Face metadata and current repository files. No weights, dependencies or production data were downloaded for evaluation.
