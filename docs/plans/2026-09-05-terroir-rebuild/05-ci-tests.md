# Branch, landing, CI and verification specification

## Safe integration path

After Gate 1, use a new protected candidate integration branch, proposed `rebuild/integration`, created from verified main. Feature PRs target it. Main auto-deploys under current repository policy, so do not integrate the rebuild into main piecemeal or assume a merge is harmless. Verify actual Railway branch routing and disable unintended candidate production routing only with explicit authorization. No settings change or branch creation occurs now.

Keep at most two ready integration PRs. Drafts may exist but do not count as completed work or available throughput. One non-author integrator, selected by the per-PR table in07, locks landing, verifies exact reviewed head and current base, resolves all blocking findings, and checks actual gate evidence. Advance one base at a time. After each merge, record integration SHA and full-run ownership. Use the approved merge strategy without rebasing, force-pushing, resetting or deleting branch/worktree state. Refresh a feature by fetching and **merging its approved integration base into that branch**; conflicts belong to its single owner, followed by affected review/tests. Refresh integration from main through a reviewed merge PR, not an unreviewed base rewrite.

S uses protected serialized landing with strict latest-base checks and exact reviewed head matching. Queue, merge_group, draft aggregation and CI runner migration are optional F work, excluded from S estimates. The repository is public and organization-owned: GitHub native merge queue is eligible, currently absent. Enable only after required checks and `merge_group` workflow support work on the candidate branch. Start build concurrency1 and one PR per merge group; two ready PRs can await service. If queue enablement is delayed, use a protected serialized landing train with latest-base validation and exact-head matching. Current `strict:false` does not enforce freshness; propose strict-up-to-date checks on the candidate branch. If required protections cannot be enabled, reviewed PRs remain unmerged; an unprotected candidate is not the fallback. [GitHub queue eligibility](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/incorporating-changes-from-a-pull-request/merging-a-pull-request-with-a-merge-queue?tool=webui).

Do not use `/Users/zero/bin/zs-land`. Its inspected implementation removes worktrees and local/remote branches after merging. No advisory/allow-no-CI mode, history rewriting, shared stash, automatic deletion or hook bypass is permitted. A future landing script must prove refusing stale SHA, absent check, open blocker, wrong base and absent LAND-GO with non-mutating fixtures first. S Gate 2 controls separate candidate production admission; it does not authorize main promotion. F Gate 2 controls final main promotion/migration even if integration is green. Before W1 feature integration, Q records actual candidate protections and Railway routing proof that candidate merges cannot deploy production. Gate 1 authorizes this setup; it does not pretend the evidence exists before approval. Failure stops landing and invokes the Day 3 fallback.

Builders run focused unit/contract checks for their owned paths plus lint/type checks when needed. They do not each run the full suite. Required CI remains unchanged until an independently verified equivalent gate replaces it. One verifier dispatches full integrated runs; author jobs never reset a shared DB. CI uses ephemeral runner-local DBs. Macs use one verified project/port target with an exclusive heavy lease, if needed; a loopback host alone is not isolation.

F/optional proposal, not part of S: defer heavy work, but keep an always-running fail-closed aggregator named exactly as the required check. It passes only when the heavy predecessor actually succeeds; skipped/cancelled/failed predecessors do not pass. Include PR opened/synchronize/reopened/ready_for_review/converted_to_draft/edited activities, push to approved integration/main branches, and `merge_group: checks_requested`. This requires explicit coverage of draft→ready, retarget, failed prerequisites and merge-group synthetic heads. Preserve unfiltered PR target coverage. Do not copy a branch filter that accidentally excludes integration.

Use cancellation only for superseded PR heads. Do not cancel the integrated/main or merge-group evidence being used for acceptance. Do not duplicate all coverage work in a second job merely to retain its display name. The existing explicit contract subset repeats124 tests included in Vitest; removing that repetition is optional only after proving identical environment, discovery and failure semantics. Keep it while correctness is uncertain.

F/optional runner canary: one existing full suite, identical reviewed SHA, seed, environment and one Playwright worker, once on ubuntu-latest and once on Blacksmith4vCPU. Compare named test inventory, passes/skips/failures, setup/test/total time, cost and cold/warm cache. Repeat only for a specific cache/variance question. Identical red results prove parity only, not release readiness. Sharding canary later splits across two separate runner/DB/auth fixtures and verifies union/disjoint tests and equal outcomes. Require three integrated green runs with no missing tests before adopting two shards. Do not jump to four shards.

Cache only dependency/browser binaries or deterministic build artifacts keyed by OS/architecture/Node/pnpm/lock/browser version. No active DB volumes, Auth sessions, credentials or fixture state. Measure where time goes: dependency install median2s; tests95.5s, Supabase57s and browser setup28s are larger opportunities. [Blacksmith caching](https://docs.blacksmith.sh/blacksmith-caching/dependencies-actions), [GitHub event semantics](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows), [required-check skip semantics](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/defining-the-mergeability-of-pull-requests/troubleshooting-required-status-checks).

S stays at WIP ≤2. F may increase integration WIP from2 to3 only after at least six accepted slices show disjoint ownership, no stale-base landings, passing relevant full coverage, <20% integration rework and available independent reviewers; CI p95 queue+setup under2 minutes across at least10 recent jobs. These are proposed thresholds. Reduce to1 on fixture collisions, twice-failed gate, stale-base incident or review backlog. Source throughput remains separate from runner concurrency.

## Test/eval artifacts before each track starts

The artifact specification below is complete planning work; test implementation/execution begins only after Gate 1. Before a feature author edits its boundary, Q records requirement IDs, fixture seed/schema, current characterization, target expected outputs, negative cases and command/evidence location. Existing defects get an explicit superseded expectation. Authors cannot change acceptance to match their implementation without a logged requirement decision.

`tests.csv` maps all35 R outcomes plus S1–S7 to proposed verification artifacts. owner identifies the artifact lead(s), while s_owner names active S responsibility and implementation_slices identifies where the contract/consumer is exercised; none grants extra write ownership. A broad outcome may have an F-only sub-eval and a different S-bounded eval (for example EV-06/E-031 versus EV-12/E-031). EV-05 S concerns candidate fixture/replay/parity and its backup manifests only; legacy transformation parity remains F-only. Shared fixtures define two businesses, two venues, actor/grant variants,375/750/1500ml formats, unknown/NV vintages, currenciesUSD/EUR, ambiguous producers and crash/replay keys. Unit mocks test parsing; persistence/RLS acceptance must use real isolated SQL.

Provisional S performance workload: three concurrent staff, two businesses/two venues, 250 approved catalog records, 1,000 lots and 5,000 events, all synthetic. Cellar/lookup API p95 ≤1 second; receipt commit p95 ≤1.5 seconds; mobile first-useful view p95 ≤2.5 seconds under a recorded device/network profile. Capture ≥200 requests per operation with errors, cold/warm results and query plans; 1,000 replay attempts must produce zero duplicate effects and isolation breaches remain zero-tolerance. These smaller pilot budgets require Gate 1 acceptance, are not measured results and do not establish large-group scalability. S replaces no surviving legacy route, so S performance acceptance uses target-only budgets and is labelled non-comparable. Q may retain an informational legacy characterization if its logical workload matches, but legacy-to-candidate improvement is not an S gate. Before any F replacement of a surviving path, capture its current baseline using equivalent logical workloads mapped to the appropriate schema, not identical physical tables. Record environment and fixture hash; test the candidate on approved CI/hosting, not production load. Larger 50,000-event/device fleets are deferred, not silently claimed as passed.

Object restore artifact EV-06/EV-12: inside the protected boundary enumerate every selected object key, bucket, byte length, content SHA-256 and source relationship; restore bytes and compare100% counts/lengths/hashes, report missing/extra/mismatched objects. Verify authorized read and denied cross-business/signed-out/revoked access. Metadata-only equality fails. Retain content manifests in protected storage; only redacted aggregate results leave it.

Count test identities and skips, not just exit codes. The current required five E2E include mocked receipt persistence; add the real canary. Current full27 skips must get named scope dispositions; selected S skips are failures. Deferred F tests remain documented and preserved, with no claim of complete coverage. Deployed health must report exact merge SHA and Railway SUCCESS plus actual route/DB smoke evidence; clean Git and passing unit tests do not establish release completion.
